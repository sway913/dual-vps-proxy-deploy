# Reality 目标生命周期

Reality 目标是运行依赖，不是部署时填一次就永久可靠的常量。普通 TLS 可达、`xray tls ping` 成功和低延迟只用于缩小候选范围；真实 VLESS/Reality 连接才是采用依据。

## 规划候选

1. 在实际承载 Reality 入站的 VPS 本机运行 `plan_reality_targets.py`。
2. 默认使用至少六轮探测并保留间隔；所有轮次都必须成功。
3. 优先全球分布、长期稳定、TLS 1.3 正常的站点。地区性高校、教育网、政府站点可能依赖单一地区路由，只能人工复核，不能自动采用。
4. 同 ASN 和最低延迟只是弱信号。不得为了几毫秒延迟牺牲跨网络、跨时间稳定性。
5. Cloudflare 等官方文档提示存在转发风险的 ASN 不自动采用。
6. 不固化任何历史域名；每次新部署都重新规划。

规划器输出 `PROVISIONAL_TARGET`，表示临时候选，不表示可以直接发布。

## 真实端到端筛选

对排名靠前的候选使用与生产一致的 Reality 密钥、Short ID、flow、RAW/XHTTP 参数创建临时入站。临时端口只允许测试源 IP，且不加入订阅。

从另一台 VPS 或用户日常网络创建只监听 `127.0.0.1` 的临时 Xray 客户端，并同时验证：

- RAW/Reality 能连续五次建立新连接；
- XHTTP/Reality 能连续五次建立新连接；
- 每次获取的出口 IP 与预期服务器一致；
- 服务端日志出现对应 UUID/email，而不是只有 TCP 端口连通；
- 完成其他部署步骤、至少间隔五分钟后，再重复一轮。

可使用 `scripts/verify_reality_e2e.py` 执行一轮多入口验证。客户端 JSON 必须预先由部署流程生成，权限为 `0600`，且所有 SOCKS 入站只监听回环地址。脚本结束后会停止它启动的 Xray 进程，但调用方仍负责删除临时配置。

任意一次认证、HTTPS 请求或出口 IP 检查失败，该候选都不能进入生产。不要用重启服务掩盖目标不兼容或路由波动。

## 正式写入不变量

确定目标后，以下位置必须在同一事务中保持一致：

- Xray Reality `target`/`dest`；
- Xray Reality `serverNames`；
- Clash 各相关节点的 `servername`；
- Base64 聚合内各分享 URI 的 `sni`；
- 部署凭据描述或后续订阅生成源中的 SNI。

先创建权限受限的临时回滚副本，生成新文件并用 Xray、Mihomo 和 Base64 解码检查验证；再原子安装、只重启受影响服务。真实外部验收通过后删除临时备份。

## 运行期故障处理

当同一服务器的 RAW 与 XHTTP 同时超时：

1. 先检查进程、监听、资源、时钟和防火墙，不立即重启。
2. 查看刚才用户测试对应的服务端日志。没有认证记录时，重点检查 SNI、客户端缓存和 Reality 目标；已有 accepted 记录时再检查出口与 DNS。
3. 从 Reality 服务器本机连续测试当前目标 TLS，从另一网络测试同一目标，区分目标全局故障与服务器到目标的路由故障。
4. 在临时端口上对新候选做真实 Reality 筛选，不能只凭 curl 或 `xray tls ping` 替换生产。
5. 按“正式写入不变量”同步服务端、两类订阅和凭据描述，校验后重启受影响服务。
6. 外部验证直连 RAW、直连 XHTTP、中转 RAW、中转 XHTTP 的实际出口，并让客户端刷新订阅。
7. 删除测试进程、临时端口、防火墙规则、凭据和回滚文件。

如果目标再次出现间歇性失败，直接淘汰该候选并回到真实端到端筛选；不要在两个已发生路由故障的目标之间反复切换。
